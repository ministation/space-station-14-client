## Мобильная панель 0.7.0

Раскладка считается в `MobileControlsOverlay.ArrangeOverride`, размеры кнопок 130 / 118 / 102 логических
пикселей на `mobile.controls_scale` 1.5, стики 127 на `mobile.thumbstick_scale` 1.1, общий `fit` по короткой
стороне (0.5..1.3). Что важно знать при следующей правке:

- Каждый кластер (4 кнопки у правого стика, 5 у левого) раскладывается одним размером: сначала ищется
  наибольший общий коэффициент 1.00..0.60, при котором все кнопки кластера влезают, и только потом кластер
  ставится на экран. Поэтому внутри кластера нет разнобоя, но кластеры могут отличаться по размеру.
- Углы заданы веером (правый 100/145/190/235, левый 80/35/125/170/300), кнопка отклоняется от своего угла
  шагами по 15 градусов и уходит наружу не больше чем на 3 кольца (потом 6). Верхний предел кольца и есть
  защита от "кнопка улетела в угол экрана".
- Порядок отрисовки: панель добавлена в `RootControl` между `StateRoot` и `WindowRoot`. `ScreenRoot` сам
  встаёт на позицию 2, поэтому фактический порядок: MainViewport, StateRoot, ScreenRoot, панель, WindowRoot.
  Окна контента (WindowRoot) всегда выше панели, HUD (StateRoot) ниже.
- Безопасные поля: хост читает `DisplayCutout` и передаёт `mobile.safe_area_left/right/top/bottom` в
  физических пикселях, движок делит их на `display.uiScale` и берёт максимум с процентным полом.
- Прозрачность: `mobile.controls_opacity` по умолчанию 0.6, лаунчер даёт 0.4..0.9.
- После первого расклада панель пишет `mobile-controls-debug.txt` в файловую папку приложения: порядок
  корней, прямоугольники стиков и всех кнопок. На эмуляторе файл не появляется, потому что клиент падает
  на прототипах контента до первого кадра.

Проверка раскладки без устройства: симулятор на Python повторяет те же формулы, прогон по 55 сочетаниям
разрешений и `uiScale` (1920..3120 по ширине, ui 1.4..2.0) даёт 9/9 кнопок без наложений, коэффициент
кластера 0.85..1.0 на типичных телефонах.

Собранный APK 0.7.0: sha256 `ce4b934142541d28b8aca048b7ad999ef4d3c18845a43ef76f6d6ccec83cf656`,
50016336 байт, лежит на GitHub (`android-v0.7.0`) и на CDN в `/android/latest/` и `/android/0.7.0/`.

### Раскладка 0.7.0, финальный вариант

-INV` и `PULL` уехали в верхнюю полосу: семь ячеек (ESC, EDIT, KB, ALT, EXAM, INV, PULL) делят ширину
экрана поровну. На стиках осталось по одной руке: справа USE / INTER / SEC / THROW, слева HAND / DROP / BAG.
- Углы веера закреплены за кнопками (справа 88 / 126 / 164 / 202, слева 90 / 124 / 56), поиск сначала
  отодвигает кнопку наружу и только потом поворачивает, поэтому подписи не меняются местами между
  разрешениями.
- Благодаря семи ячейкам все кнопки стиков остаются исходного размера (130 / 118 / 102 на scale 1.5),
  общий коэффициент кластера 1.0 на телефонах 960..1560 логических пикселей по ширине.

### UI scale в лаунчере больше не уменьшает панель

Размеры в раскладке логические, а значит зависят от `display.uiScale`. Раньше при переключении UI scale
в лаунчере с 2.0 на 1.5 панель становилась на четверть меньше физически. Теперь movestyle такой:
- `fit` считается от физического вьюпорта: `fit = clamp(min(physW, physH) / 1440, 0.5, 1.3)`;
- в `scale` зашит обратный множитель `min(2 / uiScale, 2)`, так что физический размер кнопок и стиков
  не меняется при любом UI scale.
На базовом значении 2.0 числа не изменились, это видно по симуляции: 2400x1080 даёт те же
292 / 266 / 230 физических пикселей при ui 1.25, 1.5, 1.75 и 2.0.

### Где на самом деле живёт игровой HUD

По исходникам контента (`DefaultGameScreen.xaml.cs`): TopLeft (топбар и панель действий) - левый верх,
Chat и Alerts - правый верх, Ghost - низ по центру с отступом 80, Inventory - левый низ (5),
Hotbar - низ по центру (5), Targeting - правый низ (5). Всё это ниже панели по порядку отрисовки.
Практический вывод: на 540 логических пикселях по высоте свободна только средняя полоса, а углы заняты
HUD. Поэтому верхняя полоса из семи ячеек частично идёт поверх чата, а THROW может заходить на хотбар.
Лечится не панелью, а размером интерфейса игры: UI scale 1.5 в лаунчере (теперь безопасно для панели).

### Проверка раскладки по разрешениям (0.7.0, финальная политика)

Симулятор повторяет C# один в один: семь верхних ячеек, веер с фиксированными углами, рост кольца до
поворота, подбор k от 1.0 до 0.6 с ограничением кольца 3, затем 6. Прогон 64 сочетаний (ширина 640..3120,
высота 360..1440, uiScale 1.25..2.0):

- все реальные телефоны (физическая высота 720 и больше) раскладываются при k = 1.0, то есть в исходном
  размере кнопок, без уменьшения кластера;
- не раскладываются только экраны с физической высотой 540 и 360 (крошечные или сплит-скрин), там
  срабатывает аварийный путь: кнопки уменьшаются до 0.6 и прижимаются к рамке, возможны наложения.

Практический вывод: при спорных отзывах о размере кнопок виновато не разрешение, а положение HUD.

### Сколько именно панель задевает HUD (2400x1080, физические пиксели)

Из контента: чат - TopRight с отступом 10 и минимальным размером 465x225 логических; хотбар - низ по
центру (второй хотбар на 6 слотов + панель статуса 125 + руки, слот 64 логических); инвентарь - левый низ;
таргетинг - правый низ.

Пересечения кнопок правого кластера с чатом (площадь пересечения в физических px^2):

| uiScale | USE | INTER | SEC | THROW |
|---|---|---|---|---|
| 2.0 | 75 594 | 54 590 | 0 | 0 |
| 1.5 | 41 166 | 18 983 | 0 | 0 |
| 1.25 | 23 953 | 2 849 | 0 | 0 |

То есть при штатном uiScale 2.0 кнопка USE на треть уходит под чат. Снижение UI scale уменьшает наложение,
но не убирает его: кластер висит на правом краю, а чат прижат к тому же углу. THROW при этом стоит на
хотбаре (y 820..1050 против полосы хотбара примерно 880..1060).

Полностью развести панель и HUD можно только сжатием самого HUD на мобиле: это уже контент
(чат/хотбар/панель действий), отдельный репозиторий и отдельный PR.
