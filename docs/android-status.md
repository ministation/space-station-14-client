## Мобильная панель 0.7.0

Раскладка считается в `MobileControlsOverlay.ArrangeOverride`, размеры кнопок 130 / 118 / 102 логических
пикселей на `mobile.controls_scale` 1.5, стики 127 на `mobile.thumbstick_scale` 1.1, общий `fit` по короткой
стороне (0.5..1.3). Что важно знать при следующей правке:

- Каждый кластер (4 кнопки у правого стика, 3 у левого) раскладывается одним размером: сначала ищется
  наибольший общий коэффициент 1.00..0.60, при котором все кнопки кластера влезают, и только потом кластер
  ставится на экран. Поэтому внутри кластера нет разнобоя, но кластеры могут отличаться по размеру.
- Углы заданы веером (правый 100/145/190/235, левый 80/35/125/170/300), кнопка отклоняется от своего угла
  шагами по 15 градусов и уходит наружу не больше чем на 3 кольца (потом 6). Верхний предел кольца и есть
  защита от "кнопка улетела в угол экрана".
- Порядок отрисовки: панель добавлена в `RootControl` между `StateRoot` и `WindowRoot`. `ScreenRoot` сам
  встаёт на позицию 2, поэтому фактический порядок: MainViewport, StateRoot, ScreenRoot, панель, WindowRoot.
  Окна контента (WindowRoot) всегда выше панели, HUD (StateRoot) ниже.
- Безопасные поля: хост читает `DisplayCutout` и передаёт `mobile.safe_area_left/right/top/bottom` в
  физических пикселях, движок делит их на `display.uiScale` и берёт максимум с процентным полом.
- Прозрачность: `mobile.controls_opacity` по умолчанию 0.6, лаунчер даёт 0.4..0.9.
- После первого расклада панель пишет `mobile-controls-debug.txt` в файловую папку приложения: порядок
  корней, прямоугольники стиков и всех кнопок. На эмуляторе файл не появляется, потому что клиент падает
  на прототипах контента до первого кадра.

Проверка раскладки без устройства: симулятор на Python повторяет те же формулы, прогон по 55 сочетаниям
разрешений и `uiScale` (1920..3120 по ширине, ui 1.4..2.0) даёт 9/9 кнопок без наложений, коэффициент
кластера 0.85..1.0 на типичных телефонах.

Собранный APK 0.7.0: sha256 `ce4b934142541d28b8aca048b7ad999ef4d3c18845a43ef76f6d6ccec83cf656`,
50016336 байт, лежит на GitHub (`android-v0.7.0`) и на CDN в `/android/latest/` и `/android/0.7.0/`.

### Раскладка 0.7.0, финальный вариант

-INV` и `PULL` уехали в верхнюю полосу: семь ячеек (ESC, EDIT, KB, ALT, EXAM, INV, PULL) делят ширину
экрана поровну. На стиках осталось по одной руке: справа USE / INTER / SEC / THROW, слева HAND / DROP / BAG.
- Углы веера закреплены за кнопками (справа 88 / 126 / 164 / 202, слева 90 / 124 / 56), поиск сначала
  отодвигает кнопку наружу и только потом поворачивает, поэтому подписи не меняются местами между
  разрешениями.
- Благодаря семи ячейкам все кнопки стиков остаются исходного размера (130 / 118 / 102 на scale 1.5),
  общий коэффициент кластера 1.0 на телефонах 960..1560 логических пикселей по ширине.

### UI scale в лаунчере больше не уменьшает панель

Размеры в раскладке логические, а значит зависят от `display.uiScale`. Раньше при переключении UI scale
в лаунчере с 2.0 на 1.5 панель становилась на четверть меньше физически. Теперь movestyle такой:
- `fit` считается от физического вьюпорта: `fit = clamp(min(physW, physH) / 1440, 0.5, 1.3)`;
- в `scale` зашит обратный множитель `min(2 / uiScale, 2)`, так что физический размер кнопок и стиков
  не меняется при любом UI scale.
На базовом значении 2.0 числа не изменились, это видно по симуляции: 2400x1080 даёт те же
292 / 266 / 230 физических пикселей при ui 1.25, 1.5, 1.75 и 2.0.

### Где на самом деле живёт игровой HUD

По исходникам контента (`DefaultGameScreen.xaml.cs`): TopLeft (топбар и панель действий) - левый верх,
Chat и Alerts - правый верх, Ghost - низ по центру с отступом 80, Inventory - левый низ (5),
Hotbar - низ по центру (5), Targeting - правый низ (5). Всё это ниже панели по порядку отрисовки.
Практический вывод: на 540 логических пикселях по высоте свободна только средняя полоса, а углы заняты
HUD. Поэтому верхняя полоса из семи ячеек частично идёт поверх чата, а THROW может заходить на хотбар.
Лечится не панелью, а размером интерфейса игры: UI scale 1.5 в лаунчере (теперь безопасно для панели).

### Проверка раскладки по разрешениям (0.7.0, финальная политика)

Симулятор повторяет C# один в один: семь верхних ячеек, веер с фиксированными углами, рост кольца до
поворота, подбор k от 1.0 до 0.6 с ограничением кольца 3, затем 6. Прогон 64 сочетаний (ширина 640..3120,
высота 360..1440, uiScale 1.25..2.0):

- все реальные телефоны (физическая высота 720 и больше) раскладываются при k = 1.0, то есть в исходном
  размере кнопок, без уменьшения кластера;
- не раскладываются только экраны с физической высотой 540 и 360 (крошечные или сплит-скрин), там
  срабатывает аварийный путь: кнопки уменьшаются до 0.6 и прижимаются к рамке, возможны наложения.

Практический вывод: при спорных отзывах о размере кнопок виновато не разрешение, а положение HUD.

### Сколько именно панель задевает HUD (2400x1080, физические пиксели)

Из контента: чат - TopRight с отступом 10 и минимальным размером 465x225 логических; хотбар - низ по
центру (второй хотбар на 6 слотов + панель статуса 125 + руки, слот 64 логических); инвентарь - левый низ;
таргетинг - правый низ.

Пересечения кнопок правого кластера с чатом (площадь пересечения в физических px^2):

| uiScale | USE | INTER | SEC | THROW |
|---|---|---|---|---|
| 2.0 | 75 594 | 54 590 | 0 | 0 |
| 1.5 | 41 166 | 18 983 | 0 | 0 |
| 1.25 | 23 953 | 2 849 | 0 | 0 |

То есть при штатном uiScale 2.0 кнопка USE на треть уходит под чат. Снижение UI scale уменьшает наложение,
но не убирает его: кластер висит на правом краю, а чат прижат к тому же углу. THROW при этом стоит на
хотбаре (y 820..1050 против полосы хотбара примерно 880..1060).

Полностью развести панель и HUD можно только сжатием самого HUD на мобиле: это уже контент
(чат/хотбар/панель действий), отдельный репозиторий и отдельный PR.

### 1.0.11: чат снова открывает клавиатуру

Выпущено 13 ноября 2026: тег android-v1.0.11, android/latest и android/1.0.11 как space-station.apk,
sha256 015c7a3f96474d408f93e95e01ffbf5aeb7d268a83bc696685d3c4f014f5da9f, versionCode 76. Патч движка: 122 файла, 11010 строк, sha256
37118a1cdc33057cc4b570c21bf443606176d93c341e090e2e362203d9c15fbd; git apply --check на чистом v295.0.2 проходит, diff -r с vendor даёт 0 строк.

- Не работало: тап по строке ввода чата не открывал экранную клавиатуру, писать в чат было нельзя.
- Причина: с 0.8.8 тап по HUD-контролу не идёт путём мыши. InjectTouchClick в
  UserInterfaceManager.Input.cs сам находит контрол под пальцем и отправляет ему UIClick, а фокус в
  движке ставит только HandleCanFocusDown на пути мыши: ControlFocused = контрол, и если
  CanKeyboardFocus и KeyboardFocusOnClick, то GrabKeyboardFocus. LineEdit (строка чата) на одиночный
  UIClick фокус не берёт, он только выделяет слово по двойному клику. KeyboardFocused оставался пустым,
  KeyboardFocusEntered не вызывался, движок не делал TextInputStart, а без него SDL и хост не показывают
  IME. Показ клавиатуры, подключённый к TextInputStart в 0.9.3, получал управление только после фокуса,
  которого не было.
- Решение: InjectTouchClick на нажатии повторяет фокусную часть HandleCanFocusDown (снимает прежний
  keyboard focus, ставит ControlFocused, берёт keyboard focus, если у контрола KeyboardFocusOnClick),
  на отпускании сбрасывает ControlFocused, как HandleCanFocusUp. Тап по строке чата теперь даёт фокус
  LineEdit, тот просит TextInputStart, хост показывает клавиатуру. Тап по другому HUD снимает фокус и
  прячет клавиатуру, как клик мышью на ПК.
- Проверка: временный тест в Robust.Client.IntegrationTests на headless UserInterfaceManager:
  InjectTouchClick в LineEdit ставит KeyboardFocused на него, отпускание фокус не снимает. Тест проходит,
  в патч не добавлен (движок пересоздаётся fetch-engine.sh). Патч проверен git apply --check на чистом
  v295.0.2, применение совпадает с vendor.
- На телефоне не проверено: эмулятор без аккаунта SS14 до чата в игре не доходит. Проверен фокус в
  движке, показ IME на устройстве не проверялся.

- Решение: TouchHitsWindow в GameController.Input.cs и в MobileControlsOverlay.cs теперь считает
  окном любой контрол, у которого в предках есть BaseWindow (движковый базовый класс всех окон

- На телефоне по-прежнему не проверено, устройства нет. Но в коде причина однозначная: при

- Причина: в мобильном лайтмапе окклюдеры растеризуются в solid-клетки. Клетка пола рядом со стеной
  своим центром попадает ровно на границу полигона стены, поэтому тоже становится solid. Поиск в
  ширину заливает пол, доходит до такой клетки, но из solid-клеток свет не расходится, и клетка
  самой стены никогда не получает света. На ПК это лечит light.wall_bleed (два экранных прохода
  BlurOntoWalls и MergeWallLayer), на Android cvar выключен, а в CPU-лайтмапе такого прохода не было
  вовсе, поэтому стена была чёрной даже в освещённой комнате.
- Решение: в CPU-лайтмап добавлен проход BleedMobileLightmap перед записью пикселей. Каждая
  solid-клетка берёт максимум по 8 соседям в каждом канале и получает 0.55 от него, но не меньше
  своего света. Чтение идёт из несмешанного буфера, поэтому внутрь толстых стен свет не расходится
  глубже одной клетки. Клетки пола и остальные не-solid-клетки не меняются, шейдеры и теневые
  проходы не трогались, новых GPU-проходов нет. Цена: около 24-29 мкс на кадр на x64 (лайтмап
  целиком 102-196 мкс), 0 байт аллокаций.
- Проверка: tools/LightmapBench обновлён. Проверка бит в бит с эталоном 0.9.1 теперь идёт с
  выключенным bleed (иначе она бы всегда падала), а эффект проверяется отдельно: floorDiff 0,
  darkerSolid 0, в каждом сценарии 6-9 тысяч ранее чёрных клеток стен стали светлыми. Общий

### 0.8.13: шейдеры контента компилируются на мобильном GLES

Выпущено 11 ноября 2026: тег android-v0.8.13, APK на GitHub и на CDN в путях android/latest и android/0.8.13, sha256 79cc5baa4e35390e616ea0f1b51bcba26d221eba84d94bf6d72c47a90ee4bcd4, versionCode 54.

- Причина краша на телефоне: Failed to compile fragment shader for '/Textures/_Goobstation/Heretic/Shaders/hypno.swsl', 0:301: S0032: no default precision defined for variable 'float[6]'. В GLSL ES (мобильные драйверы Adreno/Mali) у фрагментного шейдера нет точности float по умолчанию, а шейдер контента собирает массивы конструктором float[6](...) и рассчитывает на эту точность. Компиляция падает, шейдеры грузятся при загрузке прототипов, поэтому клиент умирал ещё до меню. На десктопном OpenGL точность по умолчанию есть, поэтому на ПК всё работало.
- Почему движок не спасал: precision highp float для GLES дописывался в versionHeader под #ifdef FRAGMENT_SHADER, а #define FRAGMENT_SHADER добавляется уже после versionHeader. ### 0.8.1: джойстики больше не белые

Выпущено 10 ноября 2026: тег android-v0.8.1, APK на GitHub и на CDN в путях android/latest и android/0.8.1, sha256 85588ad046213091387c4c662cb604b59bb8ebf1510f827a99665ee7190c6780, versionCode 42.

- Причина белых дисков: в Color(...) с тернарным аргументом (например, `new Color(132, 139, 150, pressed ? 190 : 150)`)
  компилятор выбирает конструктор с float, а не с byte. В цвет попадали значения 132/139/150, а после перевода в
  линейное пространство они уходили далеко за единицу, и весь диск рисовался белым. Теперь ToLinear перед переводом
  приводит такие каналы из 0..255 обратно в 0..1, поэтому обод стика снова серый, как в редакторе.
- Заодно исправлен крест прицельного стика (у него был тот же тернарный цвет), раньше он тоже светился белым.
- Сохранённые позиции панели сбрасываются ещё раз (версия раскладки 3): у части игроков после обновления остались
  старые доли от редактора 0.7.x, из-за которых кнопки были меньше и стояли не на местах. После 0.8.1 игра и редактор
  снова рисуют одинаковые размеры и позиции.
